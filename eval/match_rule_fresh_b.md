# MATCH RULE (fresh set, block B), version 1, 9 Nov 2026

`eval/match_rule.md` v1 applies unchanged with these substitutions: evaluation episodes = 15, 16, 17, 35; G = positive rows of `eval/gold_fresh_b.csv`; K = 2 × |G|; L = promos fully inside 15, 16, 17, 35 in each system's frozen order (v1: `config/eval_order.yaml`; v2: its own frozen v2 order; baseline: frozen round-robin). Scored once; v1 and baseline lists are computed from the existing P07b outputs.

## 1. Why this file exists
- Block A (episodes 31–34, `eval/match_rule_fresh.md`) turned out to be a null test of v2: its v1 and v2 lists are identical at 31 of 32 positions, because those episodes hold almost none of the pairs v2 changes.
- Block B is a second fresh block, chosen by the rule in §2 so that v2 changes the kept candidates there. Its v1 and v2 outputs existed before this rule was written. Nobody has read their promo content: only counts were computed, by code, for the selection.
- Block B is not a random sample. The rule favours episodes where v1 and v2 differ, so a v2 gain here is not an estimate of the effect over the whole show.

## 2. Selection rule (verbatim; builder output only)
Eligible episodes are all episodes except the held-out episodes (1-4, 11-14, 26-29, 42-45), the DEV episodes (5-8, 19-22), the block A episodes 31-34, and episodes 46 and above. For each eligible episode, count the candidates that exactly one of v1 (outputs/runs/full) and v2 (outputs/runs/full_v2) keeps, each candidate identified by its segments (episode, first line id, last line id): the size of the symmetric difference of the two kept-candidate sets. Block B is the 4 eligible episodes with the largest count; ties go to the lower episode number. No gold file or label is read.

Result, computed by `tools/pick_block_b.py`: E17 (6), E35 (4), E15 (3), E16 (3), that is episodes 15, 16, 17 and 35.

## 3. Fixed before scoring
- Hashed in `eval/HASHES.md`: this file and `eval/gold_fresh_b.csv`, besides `config/v2.yaml` (already hashed).
- The block B L files (v1, v2, baseline) are generated by code from stored outputs and their sha256 values are sealed in `L_seal.json` before any block B gold exists. No gold file is read when an L file is made.
- v2 uses `config/eval_order.yaml` unchanged: there is no separate v2 order file. The needs_human lane is a label only and does not change the order (D66).
- No block B promo content, span, line ID or score is opened or printed before scoring; counts only.

## 4. Primary and descriptive results
- **Primary:** v2 Recall@K at τ = 0.5 (match rule §5) on block B, and the paired v2-vs-v1 contrast on G (a_i = 1 if v2 matched gold i, b_i = 1 if v1 did).
- **Everything else is descriptive:** hook-hit, hook-found, Precision@10, recall by grade, negative-hit rate, v2 vs baseline, and the τ = 0.3 and 0.7 rows. All §5 and §6 metrics and tests are as in `eval/match_rule_fresh.md` §4.
- **Block A and block B are reported separately and never pooled.**

## 5. Score once
- One scoring run on block B; its ledger entry records `scoring_runs = 1` for block B, separate from block A's. Any later run is counted and labelled "dev".
